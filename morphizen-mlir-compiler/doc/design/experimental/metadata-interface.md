# Metadata JSON Interface (Experimental)

## Overview

The `inference_get_metadata_json()` interface provides runtime introspection of compiled model metadata. This enables tools to discover input/output tensor requirements without external manifest files.

**Status**: Experimental - API may change in future versions.

## API

```c
const char* inference_get_metadata_json(void);
```

### Returns

Pointer to null-terminated JSON string stored in static `.data` section. The caller **must not** free this pointer.

### Thread Safety

Safe to call from multiple threads (returns pointer to immutable read-only data).

## JSON Schema

### Version 1.0

```json
{
  "version": "1.0",
  "inputs": [
    {
      "shape": [dimension, ...]
    },
    ...
  ],
  "outputs": [
    {
      "shape": [dimension, ...]
    },
    ...
  ]
}
```

### Fields

- **version** (string): Schema version ("1.0")
- **inputs** (array): Input tensor metadata, ordered by position
- **outputs** (array): Output tensor metadata, ordered by position
- **shape** (array of int64): Tensor dimensions
  - `-1` indicates a dynamic dimension (resolved at runtime)
  - Positive values indicate static dimensions

### Shape Semantics

Shape dimensions are extracted from the ONNX model's function signature during the ONNX→HIP conversion:

- **Static dimensions**: Concrete values from the model (e.g., `[1, 3, 224, 224]` for ImageNet inputs)
- **Dynamic dimensions**: Marked as `-1` when the model uses dynamic shapes (e.g., variable batch size)
- **Mixed shapes**: Models can have both static and dynamic dimensions (e.g., `[-1, 3, 224, 224]` for dynamic batch)

The shape information is preserved through the compilation pipeline via module attributes:
- `hipdnn.input_ranks`: Array of rank values (e.g., `[4]` for single 4D tensor)
- `hipdnn.input_shapes`: **Array of arrays** - each element is a DenseI64ArrayAttr containing one tensor's shape (e.g., `[[1, 3, 224, 224]]`)
- `hipdnn.output_ranks`: Array of output tensor ranks
- `hipdnn.output_shapes`: **Array of arrays** - each element is a DenseI64ArrayAttr containing one tensor's shape

Note: The shapes use structured arrays (not flattened) to maintain clear per-tensor boundaries and avoid fragile offset calculations.

## Example Usage

```c
#include <stdio.h>
#include <dlfcn.h>

typedef const char* (*GetMetadataFunc)(void);

int main() {
    void* handle = dlopen("model.so", RTLD_LAZY);
    GetMetadataFunc get_metadata =
        (GetMetadataFunc)dlsym(handle, "inference_get_metadata_json");

    const char* json = get_metadata();
    printf("Metadata: %s\n", json);
    // Do NOT free(json) - it points to static data!

    dlclose(handle);
    return 0;
}
```

## Implementation Details

### Code Generation

Generated by `GenerateInterfacePass` after `--convert-hip-to-llvm`:

1. **buildMetadataJson()**: Reads module attributes and constructs JSON using `llvm::json` API:
   - `hipdnn.input_ranks`: Number of dimensions for each input tensor
   - `hipdnn.input_shapes`: Flattened array of all input dimension values
   - `hipdnn.output_ranks`: Number of dimensions for each output tensor
   - `hipdnn.output_shapes`: Flattened array of all output dimension values
2. **generateMetadataGlobal()**: Creates `LLVM::GlobalOp` with internal linkage for `__metadata_json` constant string
3. **generateInferenceGetMetadataJson()**: Creates exported function that returns `AddressOfOp(__metadata_json)`

The shape attributes are set by `OnnxToHipPass::generateModuleMetadata()` which extracts shape information from the `@main_graph` function signature before transformation.

### Memory Layout

```
.data section:
  __metadata_json:
    .asciz "{\"version\":\"1.0\",\"inputs\":[...],\"outputs\":[...]}"

.text section:
  inference_get_metadata_json:
    lea rax, [__metadata_json]
    ret
```

### Why Not malloc()?

- **Zero runtime overhead**: No allocation, no deallocation, no memory leaks
- **Simplicity**: No error handling, no state management
- **Safety**: Immutable data prevents accidental corruption
- **Performance**: Single memory access, no syscalls

## Limitations

### Current (v1.0)

- No data type information (assumed float32)
- No tensor names/semantics
- No quantization metadata
- Dynamic dimensions marked as `-1` (resolved at runtime from actual input data)

### Future Enhancements

- Data type enumeration (float32, float16, int8, etc.)
- Tensor names and semantic tags
- Memory layout (NCHW, NHWC, etc.)
- Quantization scale/zero-point
- Version negotiation (semantic versioning)
- Min/max bounds for dynamic dimensions

## Testing

### Manual Verification

```bash
# Compile model to DLL
morphizen-compile demo.mlir -o test.dll --mode dll

# Check exports (Linux)
nm -D test.so | grep metadata
# 00001234 T inference_get_metadata_json

# Check exports (Windows)
dumpbin /EXPORTS test.dll | findstr metadata
# inference_get_metadata_json

# Extract and format JSON
python -c "
import ctypes
dll = ctypes.CDLL('./test.so')
dll.inference_get_metadata_json.restype = ctypes.c_char_p
json_str = dll.inference_get_metadata_json()
import json
print(json.dumps(json.loads(json_str), indent=2))
"
```
